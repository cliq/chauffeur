Chauffeur
App manual

Chauffeur keeps real Codex and Claude Code terminals organized by project, profile, group, and Git checkout. The agents keep running when you close the app.

App manual · Updated 22 September 2026 · Covers the implemented personal build, MCP communication, and orchestration. Broader release workload testing remains planned for V2.

1. First launch

This personal build targets Apple silicon and macOS 15 or later. Install the CLIs you intend to use, Git, and tmux. The team setup wizard can help you sign in. Chauffeur bundles its own background runtime and helpers; it does not install or upgrade Codex, Claude Code, or tmux.

  1. Open build/Build/Products/Release/Chauffeur.app from the project checkout. This build is signed with Leonardo Lobato’s Developer ID certificate.
  2. Check the service line in Welcome. If macOS requires background-service approval, use its link to System Settings → General → Login Items & Extensions, then return to Chauffeur.
  3. Choose Set Up Teams…. Select your agents and create a team using existing or new configurations.
  4. Return to Welcome and choose Create New Project…. Give it a name, choose that team, and add a repository or folder.
  5. In the project window, press ⌘N, review the agent preset and working directory, and choose Launch Session.
  6. Complete any native trust, sign-in, or approval prompt in the embedded CLI, then type your task.

Keep the app bundle at its registered location while the background service is in use. A project can be saved before it has folders or active agent presets; add those before launching an agent.

3. Agent Presets and accounts

Set up teams and accounts

  1. Choose Set Up Teams… on Welcome or Settings → Teams → Add Team….
  2. Select Codex, Claude Code, or both. Choose one account, multiple accounts, or not sure separately for each agent. Missing executables have installation instructions and a recheck action.
  3. Name your teams, such as Personal and Work, and select their agents.
  4. Use the current configuration, choose an existing folder, or create a separate configuration. Detected folders include claudewho and codexwho profiles. Teams can share an agent configuration while keeping the other agent separate.
  5. For new folders, choose a source (normally ~/.claude or ~/.codex) or start fresh. New destinations default to ~/.claude-<team> or ~/.codex-<team>. Select settings to copy and preview the files. Plugins, connections, hooks, and Claude project history require explicit selection.
  6. Review the configuration and choose Sign in to start the embedded login terminal, or choose Sign in later. Check the account shown by your browser. The wizard checks CLI authentication status and displays account identity when available; use Recheck or sign in again if needed.
  7. Choose a default team, then select Finish to save your teams and return to Welcome.

Copying preserves the source and excludes credential files and recognized secret fields. Unsupported files or fields are reported in the preview. Existing destinations are not overwritten. Authentication stays in the agent's native storage, which can include macOS Keychain. Preview warnings identify removed nested fields and retained references into the source folder; arbitrary shell commands and referenced root scripts are not rewritten or automatically copied.

Finish validates every selected agent and configuration folder before saving teams. Missing installations or folders must be corrected first; signing in can still wait. Agent commands are resolved when used so normal CLI updates do not pin new teams to removed version directories.

Shared configuration labels mean that login and setting changes affect every team using that folder. Team names are labels, not proof of account identity. Connected means the CLI reported sign-in; it does not establish model access or remaining quota. Unknown status formats show Unable to verify.

Save and Finish Later keeps unfinished choices. Use Resume Setup… to continue. Closing the wizard detaches the login view; Cancel login explicitly stops that login. Created folders remain in place. Direct team editing and reusable launch presets remain available in Settings.

Delete a team

Select a team and click the trash button beside Edit…, or right-click it and choose Delete Team…. Confirm to delete the team and its agent preset definitions. External CLI configuration directories and session history stay intact. Teams assigned to projects, including archived projects, cannot be deleted until those projects choose another team.

Write launch arguments normally

Use spaces or newlines between arguments. Quote a value containing spaces. For example:

--model "model name"

Replace the example value with a model accepted by your CLI. The editor keeps literal -- and straight quotes; it does not apply smart-dash or quote substitution. An unfinished quote produces a validation message instead of saving.

This field is an argument list, not a shell command. Shell variables, pipelines, command substitutions, and ~ in argument values are not expanded. Chauffeur manages the working directory, configuration directory, additional repositories, its integration, and conversation resume through dedicated fields. Conflicting options are rejected. Codex’s --yolo alias is recognized and retains its native CLI meaning.

Edit, default, and archive

Use the team’s Edit… button to rename it, choose a default agent preset, or change its archived state. Use an agent preset’s Edit… button to change its settings or archived state. Archived agent presets and teams cannot launch new sessions until reopened.

Changes affect future launches in every linked project. Existing sessions retain their recorded agent preset, team revision, configuration path, and launch arguments. The underlying CLI still controls how it reads its own configuration files.

New Session prefers the project’s last successfully launched agent preset, then the team default, then an available agent preset. A failed launch does not replace that preference.

4. Projects and folders

Create a project

From Welcome, choose Create New Project…, enter a name, and select a team. Then choose one of these folder workflows:

ControlUse it to
Choose Parent Folder…Discover repositories beneath a folder. Tick the desired results, then choose Add Selected Repositories. Cancel Discovery stops an in-progress scan.
Add Folder…Add any existing folder directly, including a non-Git folder.
Start EmptyCreate the project without registering folders yet.

Discovery recognizes Git worktrees with a .git file, avoids Git internals and symlink loops, and reports locations it cannot read. Discovery results and registered folders have separate counts and scrollable lists. Save with Save Project; the project window opens and Welcome closes.

Change folders or the project’s team

Open the project’s … → Project Settings… menu. Add folders, use Relink… for a moved or unavailable folder, remove a registration, rename the project, or select another team. The sidebar’s Add Folder… and repository context menu also lead to folder management.

Aliases to the same location are treated as duplicates within one project. The same folder can belong to different projects. Removing its registration preserves the files and existing session/worktree records. Relinking or changing a team affects future launches; it does not rewrite a running session’s original paths.

Archive and reopen

In Welcome, right-click a project for Open, Rename…, Archive Project, and Reveal in Finder. Reveal opens its Chauffeur metadata folder. Archiving keeps its files and sessions and does not stop agents. Enable Archived in Welcome to find it and choose Reopen Project.

5. Windows and groups

Each project has an independent window. Click anywhere in a Welcome project row, including its name, to select it. Open the selected project with a double-click, Return, or Open Project. Opening an already-open project focuses its existing window. Use normal macOS controls to move, resize, minimize, or make a window full screen.

The header shows the project, team, and the selected checkout with its Launch Agent… and Open Shell actions. The sidebar has two modes. Repositories lists each repository with its main checkout and worktrees; a badge counts sessions needing attention. Select a checkout to see its sessions in the strip above the terminal, or the repository itself for an overview of all its checkouts. Every worktree Git reports is usable immediately; a checkout that no longer exists shows as Finished while it still has session history, and Delete Worktree… in its context menu removes the checkout and that history. Sessions lists every session with the group picker and search field. Click anywhere in a sidebar row, not only its text, to select it. Hover truncated labels to see more context; full launch paths are also available in Session Details. Use the sidebar toggle to make more room for a terminal.

Drag a session tab onto another tab in the same checkout to reorder it. The order is saved when you reopen the project. Hover over a tab to reveal its close button; closing an active agent or a busy shell asks for confirmation.

Sidebar mode, selected checkout, session and group, sidebar state, and available window geometry are saved. ⌘⇧O opens Welcome to choose another project; ⌘⇧0 also opens Welcome. Exact Space assignment after reboot is not guaranteed.

Open and close tabs

Press ⌘T for a quick choice: T immediately opens a terminal in the selected checkout; A opens agent setup. You may keep Command held for the second key. Esc cancels the picker. Use ⌃Tab and ⌃⇧Tab to move to the next and previous open tabs in that checkout. Opening a tab or moving to another one gives its terminal the keyboard, so you can type to the agent immediately.

⌘W closes the current tab and stops its session. It asks for confirmation first, unless the tab is a shell waiting at its own prompt or a session that has already ended; the prompt names the command still running. If the selected checkout has no open tabs, it closes the window. Closing the last tab leaves the window open; press ⌘W again to close it. By default, closing a tab also deletes its saved history. Enable Settings → Runtime → Keep finished sessions and save settings to retain closed sessions in Finished. Right-click a finished session and choose Delete Finished Session… to permanently remove its history.

Move through the sidebar

⌘↓ and ⌘↑ move the sidebar selection without leaving the terminal, and reveal the sidebar when it is hidden. In Repositories mode they step through each repository and its checkouts, skipping the checkouts of a collapsed repository; in Sessions mode they step through the listed sessions. The selection wraps at both ends, and the terminal of the session you land on takes the keyboard.

Groups

  1. Choose … → Manage Groups… in a project window.
  2. Enter a name and choose Add Group, rename existing groups, or archive/reopen a non-default group.
  3. Choose Save Groups. Cancel discards unsaved edits.

Every project has a Default group. The sidebar’s Agent group picker filters the view to one group or All Groups. New sessions use the current active group when valid, otherwise Default. A session keeps its group through stop and supported resume. Archived groups retain their sessions and messages but are excluded from new-launch choices.

Use Search sessions or ⌘K to find a session in the current project. This command reveals a hidden sidebar. Group boundaries apply to the experimental agent communication tools; two groups can still edit the same checkout if you launch them there.

6. Start a session

  1. Select a repository, then click + or press ⌘N. A repository’s context menu also offers New Session Here….
  2. Optionally enter a title. Select the group and agent preset, and check the displayed configuration path.
  3. Choose the repository and Work in location: its registered checkout, a registered existing worktree, or New worktree….
  4. Review the exact working directory. Expand Additional repository access and select any other project repositories the agent needs.
  5. Optionally override the model and reasoning effort for this session; the saved preset remains unchanged.
  6. Optionally enter an initial task. It is passed as the CLI’s initial prompt; you can leave it empty and type after startup.
  7. Review the integration toggle, then choose Launch Session or Create & Launch.

If another Chauffeur session uses the checkout, the sheet names it and requires Share this checkout with these sessions. Sharing is intentional collaboration on the same files. Choose a new worktree when you want a separate checkout.

Additional repositories use their displayed existing paths. A primary worktree isolates only its own repository; the other repositories remain shared checkouts. The primary repository’s main checkout is not added automatically. Codex 0.154.0 rejects additional directories with a read-only sandbox; choose a compatible native sandbox option explicitly or remove the additional paths.

Integration and basic terminal mode

New sessions start in basic terminal mode: the real terminal is fully usable, with Chauffeur messaging, delegation, and semantic activity signals unavailable. Turn on Enable Chauffeur messaging and delegation for a launch to try the experimental integration, which also enables Chauffeur’s completion/attention integration for candidate CLI versions. The integration remains labelled unverified; tested versions and practical workflows are described in MCP communication and orchestration. The choice applies only to that launch and its retries; running sessions are unaffected.

Daily Codex and Claude Code updates are accepted without a version allowlist. An executable that does not identify itself as the selected agent requires basic terminal mode or a corrected preset. Invalid configuration paths or executables fail explicitly; Chauffeur does not substitute another profile. If startup fails, correct the reported cause before choosing a fresh Launch Session. Check Previous Attempt retrieves the previous result after an uncertain response and does not silently rerun an already-recorded task.

7. Use the terminal

Type directly into the real Codex or Claude Code interface. Native commands, approvals, sign-in screens, tools, and CLI settings remain inside that terminal. Chauffeur adds organization and process continuity around them.

Checkouts and sessions

Select a worktree or main checkout to see its sessions as cards above the terminal; retained sessions sit behind Finished when Keep finished sessions is enabled. ⌘⇧] and ⌘⇧[ move between that checkout's sessions. Open Shell starts a login shell there as a session that survives closing the window.

Copy, paste, and links

Select output and press ⌘C; use ⌘V to paste. Hold Shift while dragging if the CLI captures mouse input. Command-click a link to open its associated app.

History and search

Choose History and Search or press ⌘F. Search and copy from a stable, read-only capture. Refresh captures current output when the terminal still exists.

Session Details

Use the right-sidebar toolbar button or session context menu. Review the agent, group, agent preset/revision, paths, state, branch/base commit when available, and execution controls. The adjacent Progress tab displays the session’s registered implementation progress panel.

Expand Launch Snapshot in Session Details for the recorded executable and CLI version, process ID, native conversation ID when available, arguments, and launch time. These are the values used by this session, even if its shared agent preteam has since changed.

Control-C and Escape go to the focused CLI. The CLI decides whether they interrupt work, cancel a prompt, or exit. Live terminal selection can change during redraws; use History when you need stable text.

8. Close, stop, and resume

ActionResult
Select another session or close a project windowDetach that view. Its agent keeps running and remains available under its checkout and in the Sessions list.
Quit Chauffeur / ⌘QChoose to keep all sessions running and quit, review an active session, or cancel.
InterruptSend Control-C to the selected execution. Its CLI decides how to respond.
Stop Session…After confirmation, ask the selected execution to stop gracefully. Other sessions stay running.
Force Stop…After confirmation, close that execution’s terminal if graceful stopping is insufficient.
Stop All Sessions and Quit…Review the listed live executions across projects, confirm their stops, and quit after they stop. Cancel leaves them running.
Resume ConversationStart a new CLI process using the recorded native conversation ID and original launch context.

A normal reopen attaches to the same surviving process and screen; it does not submit the initial task again. Stop All uses the targets shown in its confirmation. If one refuses to stop, the app reports it and stays open; use that session’s Force Stop action, then retry.

Choose what happens when you quit

With active sessions, quitting offers Keep All Sessions Running & Quit, Review Sessions, and Cancel. Review cancels quitting and opens one active session, preferring one needing attention. It can reopen a project window when none are open. Review does not stop a session. With no active sessions, the app quits directly.

Quit the background service

Use Settings → Runtime → Background Service → Quit Service to stop the service separately from the app. Agent processes remain running, but terminal updates and coordination pause. The service stays stopped until you choose Start Service, restart it, or reopen Chauffeur. This action controls the installed app’s managed service, not a custom test runtime.

What is preserved after an execution ends?

Chauffeur preserves the session record, its launch settings, and retained terminal captures. Codex or Claude Code manages its native conversation separately. Chauffeur’s Messages section contains messages exchanged through its coordination tools, not a separate copy of every prompt and answer typed into the CLI.

Saved terminal history is bounded by retention limits and can be evicted. It is useful for reading past output, but it is not itself a resumable conversation. Resume Conversation appears only when a native conversation ID is available.

Resume keeps the original profile and checkout paths. If a checkout has moved or was replaced, restore the original to its recorded location to resume, or start a new session in the new location. Relinking a project folder does not change an old launch snapshot.

After logout, reboot, or lost terminal ownership, the app can report Interrupted. It does not automatically rerun the task. During sleep, agent progress is not promised; the app reconnects and reconciles state on wake.

9. Worktrees

Expand a repository in the sidebar to see its other Git worktrees. Rows show the branch and directory name; hover for the full path. The repository row represents its registered checkout. Selecting a worktree opens its repository manager; its context menu can reveal it in Finder.

Creating a worktree reveals the sidebar, expands its repository, scrolls the new row into view, and highlights it. This happens whether you create it with a session or from the manager, even if the agent fails to start. Selecting another session highlights that session’s checkout.

Create a worktree and start an agent

  1. Choose New Worktree & Session… beneath a repository or from its context menu.
  2. Select the group and agent preset. Typing a title suggests a sanitized branch name; edit the branch to override it, or clear the branch to restore the suggestion. Choose a base ref (initially HEAD) and review the full destination path. Creation waits for a valid destination preview.
  3. Add an optional initial task and any explicit additional repository access.
  4. Choose Create & Launch.

The checkout is created under Chauffeur’s managed worktree storage, outside the original checkout. If creation succeeds but agent startup fails, the new checkout remains selected and reusable. Correct the launch problem and choose Launch Session; you do not need to create another worktree.

Create or register without launching

Open … → Manage Worktrees…, choose a repository, and use the branch/base-ref fields and Create Worktree. Opening it from a repository or worktree context menu selects the corresponding repository immediately. The manager displays registered worktrees and other Git checkouts. Use Register to make an existing checkout available in the session picker. Refresh Git Inventory requests a fresh scan.

Inventory updates in the background as well. External creates, moves, branch changes, and missing checkouts are reflected after reconciliation. A copied or replaced directory does not inherit the original checkout’s cleanup ownership. If a move leaves Git’s own records stale, repair those records with Git before refreshing.

Delete a worktree

Choose Delete Worktree… from a worktree’s context menu or Delete… in Manage Worktrees. The confirmation warns if uncommitted or untracked files will be permanently lost. Stop live sessions before deleting the checkout. Deletion also removes finished sessions and their saved terminal history.

Branches with no commits unique to other local branches are also deleted. Branches with unique commits are preserved. Closing a tab, stopping a session, or archiving a project never automatically removes a worktree.

Example: Create feature/search-ui for one agent and feature/search-api for another. Their checkouts of that repository are separate. If both sessions also receive access to the same additional repository, that additional checkout is still shared.

Attention includes user-input requests, failures, unread finished turns, and pending coordination messages. Select an item to open its session. ⌘⇧A cycles attention items in the current project/group/search view. Opening a completed session clears its unread completion; a native approval request still needs a response in the CLI.

Chauffeur does not infer completion from a quiet terminal. Codex 0.154.0 supplies turn completion but lacks Chauffeur approval/input detection. Claude’s candidate integration reports permission requests and completion; idle reminders do not turn a finished response into an attention request.

Use the menu bar

While the service is running, the Chauffeur cap in the menu bar lists projects with active sessions and their counts. Choose a project to open it, or use Open Chauffeur…. The menu remains available after the app quits. Its Quit action follows the same keep-running/review choice as ⌘Q; it does not stop the background service.

Enable notifications

  1. Open Settings → General and enable Show session notifications.
  2. Allow Chauffeur Notifications in the macOS prompt.
  3. Use Send Test Notification with an existing session to check delivery.

If you do not see a banner, check Notification Center and macOS Focus/notification settings. An alert includes project and session names and generic event text, without the terminal transcript or message body. Clicking it opens the right project/session, including when Chauffeur was quit. The click does not launch or resume an agent or submit input.

Notifications are off by default and require the installed app’s default background service. Disabling them clears Chauffeur’s queued/delivered alerts; re-enabling does not replay the old queue. macOS permission remains a separate system setting.

11. Appearance

Open Settings → Appearance → Theme and choose System, Light, or Dark. The choice is saved and applies immediately to all Chauffeur windows and terminal default colors.

Both light and dark appearance use the same warm orange accent family. The CLI may draw explicit colors or have its own theme setting; those remain under its control. Changing Chauffeur’s theme preserves terminal text and does not restart agents.

12. Open a project from Terminal

Choose Settings → General → Terminal Command → Install Terminal Command…. The destination is /usr/local/bin/chauffeur. macOS requests administrator authentication if that folder is not writable.

chauffeur
chauffeur ~/Projects/website
chauffeur "./folder with spaces"
chauffeur -- ./-example

With no argument, Chauffeur uses the current folder. A path can point to a repository, worktree, or a folder inside one. The command chooses the closest registered match, opens its project, and selects its repository. If multiple projects share that match, the app asks you to choose. If nothing matches, Create Project opens with the folder already added and its name prefilled. Choose a team, review the details, and save, or cancel.

Opening a folder does not start an agent. Repeated commands reuse the existing project window. After updating or moving the app, choose Reinstall Terminal Command… in Settings → General. It remains available even when the command is already installed and points it at this app’s bundled launcher. An unrelated existing chauffeur command is preserved and reported as a conflict.

13. History, retention, and stored data

History is a read-only capture of terminal output, including the active screen and retained scrollback. Typing or pasting into it does not reach the agent. The runtime captures output approximately every five seconds and when history is requested. A retained capture remains readable after its terminal ends.

Open Settings → Runtime → Retention and Delegation, change the fields, then choose Save Settings.

SettingDefaultEffect
Scrollback lines10,000Limits retained history. Reducing it trims saved captures; new terminals use the new live-buffer limit.
Snapshot budget (bytes)268435456 (256 MiB)Limits total encoded saved captures. Old ended/orphaned captures are removed first, then older live captures if necessary. Each capture also has a 4 MiB limit.
Completed message history (days)90Cleans up old acknowledged, failed, and cancelled coordination messages. Queued and received messages remain.
Live delegated children per parent4Bounds experimental delegation. The control allows 1–32; nested delegation is not supported.

Coordinators and delegated workers retain protected captures that are excluded from automatic budget eviction; scrollback and per-capture limits still apply. Settings shows saved-history file count and size. An evicted capture cannot be recovered by Chauffeur. Output produced since the last capture can be lost if the terminal owner is lost. Retention does not delete native CLI conversations, credentials, project files, or worktrees.

Where things live

~/Library/Application Support/Chauffeur/
  preset-sets/       Team and agent preset metadata
  projects/          Projects, groups, sessions, worktree records, window state
  worktrees/         Chauffeur-managed Git checkouts
  runtime/          Service state, message ledger, saved terminal captures

~/Library/Logs/Chauffeur/   Bounded runtime logs

Metadata is editable JSON with stable IDs. The service detects external changes and refuses stale editor saves instead of overwriting newer data. If you hand-edit or restore metadata, preserve its IDs and ownership relationships; reopen an editor after an external change. Invalid files are reported with their paths and retained for repair.

These folders do not replace backups of your repositories or CLI profiles. Terminal captures can contain anything the CLI printed. Use the diagnostics export described below when you need a report designed for troubleshooting.

14. MCP communication and orchestration

Chauffeur’s local MCP connection gives an agent tools to discover peers, exchange messages, and launch or manage workers. You ask the agent to use these tools in its normal terminal; you do not need to configure an MCP server or copy session credentials yourself. Codex and Claude Code can communicate with each other.

Prepare sessions and skills

  1. Choose a project and an active agent group. Sessions must belong to the same project and group to communicate. A shared folder alone does not put them in the same group.
  2. Launch each participating session with Enable Chauffeur messaging and delegation turned on. A session already running in basic terminal mode needs a fresh launch with integration enabled.
  3. Check Settings → Agent Presets → Chauffeur Skill…. chauffeur, chauffeur-orchestrator, and implementation-progress are linked automatically. The sheet shows their status, paths, versions, and guidance.

The chauffeur skill teaches the operational tools. The chauffeur-orchestrator skill teaches a coordinator to break down a plan, assign fresh workers, and review their results. Codex discovers the bundled skills through ~/.agents/skills/, shared across Codex profiles. Claude discovers them in each team’s configured Claude home under skills/, or ~/.claude/skills/ when no custom home is set.

Links are created at runtime startup, setup completion, and team creation or directory changes. They point to one managed source that updates when the updated Chauffeur runtime starts. Refresh repairs missing links. An existing unrelated file, directory, or link is preserved as a conflict; use Show in Finder, move the conflicting item aside if appropriate, then refresh. CLI policies can disable skill loading; restart the CLI if its skill list does not refresh. Skills are also discoverable outside Chauffeur, but its MCP connection is supplied only to sessions launched with integration enabled.

Track implementation progress

The implementation-progress skill creates a browser panel showing the task’s phases, optional steps, current activity, and estimated completion. Chauffeur can display that same panel in the right sidebar beside Session Details. The browser panel continues to work independently.

This skill is bundled and auto-installed with Chauffeur, including its script and HTML template. It registers panels automatically using the session’s local connection, even with messaging and delegation disabled. Launch an agent session and ask:

Use the implementation-progress skill while implementing
docs/plans/search-improvements.md. Create a panel with phases for discovery,
implementation, and verification. Keep the activity and phase states
current as you work so I can follow along in the Progress tab.

In Codex, you can explicitly invoke the skill with $implementation-progress. The agent creates the panel files in its chosen directory. The bundled script automatically connects them to its own session; no separate registration tool is needed. You do not need to enter paths into Chauffeur.

  1. Open the session’s right sidebar using the toolbar button or session context menu.
  2. Select Progress. Its HTML panel refreshes every two seconds; ordinary progress updates need no further registration calls.
  3. Use Open in Browser for the standalone panel or Reveal JSON to locate its companion data file.

Progress reflects the agent’s explicit updates, not automatic observation of its tools. The percentage is a rough phase-based estimate, not elapsed time or an ETA. An update older than 20 minutes is marked stale. A completed progress panel does not itself verify the work or change the session’s execution state.

To use this alongside chauffeur-orchestrator, ask each worker to create and update its own panel with the bundled skill. Meaningful changes to a worker’s JSON wake the coordinator’s inbox wait, allowing it to read progress without repeatedly polling the file. The coordinator can also maintain an overall panel. Keep the saved plan and session IDs as usual; panels supplement that record. See the orchestration example below.

No progress panel means this session has no registered files. Ask the agent to run the bundled script’s show command for its existing panel; each command retries registration. If the local connection is unavailable, the standalone browser panel still works. If the HTML is missing or cannot load, Chauffeur shows the JSON progress instead; Retry HTML is available after a loading error. Unreadable JSON is reported while Chauffeur retries, retaining the last readable progress when available.

The association survives runtime restarts while the session is retained. Its files must remain on disk, so ask the agent to use a persistent output directory if you need the panel later. If files move, ask it to register the new paths. To disconnect a panel, ask the agent to unregister it; this leaves the files intact. Live Activities are not included in this version.

On iPhone: sessions with registered progress show a progress bar and current activity in the session list. Open a terminal, tap … → Progress, and view the full registered HTML panel on its own screen. It refreshes while open. If no HTML is registered, the screen shows the available JSON summary; disconnected screens keep the last received progress marked as offline. Update Chauffeur on both the Mac and iPhone to use this feature.

Example: ask another agent for a review

Launch two sessions in the same group, with clear titles such as Implementation and Review. In the Implementation terminal, enter:

Use the chauffeur skill. Discover the sessions in this group and send
Review a message asking it to inspect my changes to Sources/Search.swift.
Include the file path and ask for findings without editing files.
Wait for its reply in the Chauffeur inbox.

In the Review terminal, enter:

Use the chauffeur skill. Read my Chauffeur inbox, review the requested
changes without editing files, and reply to the original message with
findings and any verification you performed. Acknowledge it after processing.

The agent obtains session IDs through discovery, sends a message, and replies using the received message’s ID. References identify relevant files or context; sending a path does not attach the file or grant access to it. Give the receiving session the repository access it needs when launching it.

Messages wait in the recipient’s inbox until the agent reads them. Sending or replying to a message does not start a new turn in an idle session.

For automatic interaction, use MCP delegation and follow-up to start worker turns. See Run a plan through fresh worker sessions.

Session Details → Messages shows the sender, recipient, body, references, time, and delivery state. Received by integration means a tool fetched the message; Acknowledged by agent records acknowledgement. Neither means the requested work passed review.

Cancel Queued Message is available while a message is still queued.

Run a plan through fresh worker sessions

  1. Write or choose a plan with the desired outcome, constraints, and acceptance criteria. A repository file such as docs/plans/search-improvements.md makes it easy to resume later.
  2. Launch a normal, user-created session to act as the coordinator, in the checkout and group you want to use. Enable Chauffeur integration.
  3. Ask it to use chauffeur-orchestrator. In Codex, you can explicitly invoke it with $chauffeur-orchestrator; naming the skill in your request also makes the intended workflow clear.

The coordinator calls chauffeur_delegate to launch each worker and run its initial prompt. You do not need to type into the new terminal. Workers remain visible and interactive, so you can inspect their progress or intervene.

While a worker runs, the coordinator waits for its report using chauffeur_inbox, with waitSeconds: 300. Each call waits for up to five minutes and returns immediately when a message arrives. Chauffeur suspends the wait rather than repeatedly polling its inbox. When the report arrives, it reviews the result and starts the next task or requests corrections. This lets the plan advance without user input.

An empty response means the wait expired, a worker changed state (for example, stopped or needs attention), or its registered progress JSON changed. The coordinator checks delegation status and waits again if work is still underway. It acknowledges processed messages so they do not return repeatedly.

The bundled implementation-progress script automatically registers each worker’s panel through its session connection. The coordinator finds that path in delegation status and reads it after a progress change; timestamp-only updates do not wake the wait.

New and resumed sessions receive the longer MCP timeout automatically; an already-running CLI may need to be resumed to load it.

The skill runs one worker at a time in the selected checkout, including an existing worktree, so later tasks see earlier changes. Avoid making competing edits while a worker owns a task. A group controls message routing and does not isolate files.

The coordinator chooses among the project team’s available presets. It can override the model and reasoning effort for each worker without editing the preset. Role references provide suggestions for implementation, exploration, small fixes, review, and specialist work; they are not a model allowlist.

New Session also supports launch-specific overrides, and the preset editor’s model/reasoning fields stay synchronized with launch arguments. Custom values can be saved; the provider may still reject an unavailable model or unsupported effort. Session Details records the requested launch settings.

Worker permissions: delegated workers launch with native YOLO mode enforced. This leaves the coordinator’s permissions and saved presets unchanged. Review-only and no-edit assignments are instructions to the worker, not a filesystem sandbox.

Results, corrections, and replacement

Every worker assignment includes a completion instruction: call chauffeur_report_result with the delegation ID and current turn ID, describing changes, verification, and unresolved issues. The report returns through the coordinator’s inbox while the worker terminal stays open.

The coordinator reviews the work and chooses one of these actions:

  • Accept: close the worker with an accepted outcome and advance the plan.
  • Correct: use chauffeur_follow_up to start another turn in the same worker conversation when the CLI is ready. The coordinator submits the correction prompt through MCP; you do not need to enter it yourself.
  • Replace: close the worker as replaced, confirm it has stopped, and start a fresh session linked to the previous attempt. The new worker receives the correction context and uses the same files; replacement does not reset the checkout.
  • Abandon: close the attempt with a reason and record the unresolved work in the plan.

Closure retains the session and captured terminal history. Coordinators and delegated workers have protected history that is not automatically evicted by the snapshot budget, although user-selected history limits still apply. A closed attempt is reviewed from history; further work uses a fresh session.

Normal closure captures the final output before stopping. A forced close can proceed when capture fails, with a warning that uncaptured final output may be lost.

Same-session follow-up has been verified on Codex 0.155.1 and Claude Code 2.1.278. These are tested versions, not an allowlist: follow-up checks the live terminal on each submission. It requires a completed turn and an empty, recognized composer. Busy sessions, drafts, dialogs, and unsupported layouts can prevent submission. If delivery is uncertain, inspect the operation status rather than blindly sending the prompt again; the coordinator can choose replacement instead.

MCP tool reference

These are agent tool calls, not shell commands. Discover IDs rather than guessing them. For operations with a retryKey, reuse the same key and identical arguments after a timeout; use a new key for a genuinely new operation.

Resume a plan and handle stalled workers

If the coordinator stops waiting: prompt it to continue the plan and check its Chauffeur inbox. Worker reports remain queued, but they cannot wake an idle coordinator. Automatic coordinator wake-up is not implemented; unattended orchestration depends on the coordinator keeping its inbox loop active.

The skill keeps task status, acceptance criteria, session/delegation/turn IDs, selected models, and verification in the plan file. After a disconnect, ask the coordinator to reconcile that file with discovery and delegation status before launching more work. If the original coordinator has ended, start a new user-created coordinator in the same group and ask it to recover the previous coordinator’s workers before continuing. A live coordinator cannot be replaced through recovery. Stopping a coordinator does not automatically stop its workers.

Only user-created sessions can delegate; workers cannot recursively create children. The runtime’s default live-child limit is four, configurable under Settings → Runtime → Retention and Delegation. The orchestration skill intentionally runs one worker at a time.

If a worker appears stuck: inspect its terminal and delegation status. A trust prompt or other CLI dialog may need your input. Codex errors such as “Selected model is at capacity” currently do not generate a dedicated failure notification to the coordinator; the worker may be unable to call MCP at all. Tell the coordinator what happened and ask it to close and replace that worker using another available model. Silence, a finished-turn indicator, and process exit are not substitutes for a reviewed result.

Cross-provider delegation, messages, reports, model overrides, correction turns, and retained closure have been checked with Codex 0.155.1 and Claude Code 2.1.278. The integration still carries a candidate/unverified label; broader release workload testing remains separate.

15. Recovery and diagnostics

Background service unavailable

  1. Read the service line or its issues… details.
  2. Use Start Service when offered. If approval is required, follow System Settings… to Login Items & Extensions.
  3. Use Settings → Runtime → Restart Service to re-register the current bundled runtime and reconnect.
  4. Reopen the session. Surviving owned terminals reattach; an interrupted execution requires explicit supported resume or a new session.

The background runtime reads the login-shell environment at startup. If that fails, it reports the issue and adds standard system/Homebrew executable locations to its inherited search path. A full executable path in an agent preset can resolve a missing CLI without changing global shell configuration.

Common problems

SymptomNext action

Export a diagnostic report

Choose Settings → Runtime → Export Diagnostics…, select a destination, and save. The report contains versions, paths, runtime/session states, error codes, and recent structured events. It excludes credentials, full configuration contents, prompts, arguments, messages, and terminal history. Paths can still identify account and project names, so review them before sharing.

If the service is offline, the app exports the last state received during that app run with its observation timestamp, or marks it unavailable if none was received. A cached report does not prove that a process is currently alive.

The bundled helper also supports chauffeurctl status and chauffeurctl diagnostics. In this checkout, invoke it from build/Build/Products/Release/Chauffeur.app/Contents/MacOS/chauffeurctl. The installed chauffeur command serves folder navigation; it is a different command.

17. Current release boundaries

This is a signed local personal-use build. It has not been notarized or published as a public installer, and it has no automatic updater.

  • V2: broader release workload testing—ten real sessions, four Spaces, performance measurements, and three normal workdays.
  • Current compatibility evidence: Codex 0.155.1 and Claude Code 2.1.278 pass focused cross-provider orchestration checks, including messaging, delegated results, and follow-up turns. Earlier Codex 0.154.0 and Claude Code 2.1.272/2.1.273 have separate checks with differing coverage. Because Claude Code updates daily, any Claude Code build is accepted as a candidate without per-version validation. Neither matching nor accepting a version is a claim of complete coordination support.
  • Activity: Codex approval/input detection is unavailable through the current integration. Basic terminal mode has no semantic status integration.
  • Recovery verified: real Codex and Claude sessions retain their processes and conversations through UI quit, service crashes/restarts, bundled-helper replacement, and a user-performed sleep/wake cycle. Both providers reply afterward. The terminal command’s administrator-authenticated installation and registered-folder routing also pass.
  • Profile evidence: the authorized Claude A/B test profiles use the same account. A different-account Claude check was deferred; profile labels do not establish account separation.
  • Notifications: Notification Center delivery and clicking an alert with the app quit are verified. Different Focus settings and transient banner behavior have separate limits.

Chauffeur does not provide an editor, diff/merge or pull-request UI, browser, remote agents, cloud sync, team sharing, account management, or automatic repository-wide isolation across several repositories. Use the native CLIs and your existing development tools alongside it.
